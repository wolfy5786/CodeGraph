# Relationships — Falkor/desktop

Structural chain:

`(Graph)-[:CONTAINS]->(:CodeRepository)-[:CONTAINS]->(:Root)`
`(:Folder|Root)-[:CONTAINS {order}]->(:Folder|:File)`

`(:File)-[:CONTAINS]->(top-level module/class/enum …)` continuing per SCIP tree.

Scope is the **`graph_name`** (implicit via the Falkor graph key). Each repository is its own named graph (1:1), so no `repo_name` filter is needed when traversing.

---

## Phase 1 baseline CONTAINS

| # | From | To | Notes |
|---|------|----|-------|
| 1 | Graph | CodeRepository | registration order |
| 2 | CodeRepository | Root | single anchor per repo |
| 3 | Folder / Root | Folder / File | filesystem walk |
| 4 | File | SCIP top symbol | bridging requirement |
| 5 | Semantic outer | Semantic inner | mirrors indexer hierarchy |

Whole-file overlays stop at `:File`.

## Phase 2 relationships — all SCIP-derived (no tiers, no LSP)

Every Phase 2 edge is built from the SCIP index (relationship records + occurrence stream) parsed in Phase 1, then resolved to nodes inside the repository's single named graph. Regex is only an inheritance fallback.

| Relationship | Mechanism | Fallback |
|--------------|-----------|----------|
| `INHERITS` | SCIP relationship records | language-specific `extends`-style regex |
| `IMPLEMENTS` | SCIP relationship records | `implements` regex / analogous |
| `CALLS` | reference `Occurrence` to a callable inside a callable's range | — |
| `SETS` / `GETS` | `Occurrence` `SymbolRole.WriteAccess` / `ReadAccess` on attributes → enclosing callable | — |
| `OVERRIDES` | SCIP `is_implementation` relationship | graph rule: inherited parent method of same name |
| `BELONGS_TO` | `Object` `reference_type_detail` (SCIP type) → Class | — |

Resolution example:

```text
MATCH (n {name:$simple})
WHERE labels include Class/Interface
```

Line-range matching for `CALLS`/`SETS`/`GETS` keys on **path + start_line/end_line** within the repo graph.

`InnerClass` is a SCIP label (nested class descriptor), documented in `Nodes.txt`.
